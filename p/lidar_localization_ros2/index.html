README.md

lidar_localization_ros2

Map-based 3D LiDAR localization for ROS 2 and Nav2.

Handheld Livox MID-360, ~390 m outdoors on a prior map, including stretches where the scans do not match the map and a section outside it. Each scan is matched to the map with NDT; RKO-LIO odometry predicts the motion between scans and carries the pose where matching fails. The error is 0.26 m RMSE for the whole run, in an offline replay started from the ground-truth pose (Koide Hard Point Cloud Localization Dataset outdoor_hard_02b, CC BY 4.0). How this was made · more runs

Global localization on a Unitree Go2 (upside-down Livox MID-360), started with no initial pose, on a map from a different recording: the map is built from the run Long_Stairs, the scans come from the run Outdoor2, recorded 1.5 h later along the same route (the room was not rearranged in between). The quickstart searches the whole map: each query returns 32 ranked places (circles sized by score) in 2.6 s, and the answer is accepted when two queries agree after the odometry motion. The first pose came 13.3 s into the run, 6.4 s after the first search, 0.01 m from the motion-capture ground truth. Tracking then follows the robot out of the capture room and down the long staircase, within 0.02 m (median) of the ground truth where it exists (the room). Offline replay at 1× (JEPLO dataset, GPL-3.0; this GIF is derived from it and shared under the same licence). How this was made · pairs with moved props, including failures

Give it a point cloud map (.pcd or .ply) and a LiDAR stream; it publishes the robot pose in the map. It finds the starting pose by itself, uses odometry and IMU when you have them, and works standalone or as the localization source for Nav2.

Install

ROS 2 Jazzy is the main target; Humble is supported. Foxy is end-of-life and supported on a best-effort basis: CI builds and tests it, and its differences are listed in the changelog under Unreleased.

All of them build from main. The old foxy, humble and jazzy branches are no longer kept; their last commits are the tags archive/foxy, archive/humble and archive/jazzy. ROS 2 Dashing, which main does not support, has the frozen dashing branch.

mkdir -p ~/lidarloc_ws/src
cd ~/lidarloc_ws/src
git clone https://github.com/rsasaki0109/lidar_localization_ros2.git
cd lidar_localization_ros2
scripts/bootstrap_colcon_workspace.sh --build
source ~/lidarloc_ws/install/setup.bash

This builds ndt_omp_ros2 and this package, about 30 minutes on an 8-core machine. small_gicp is optional (SMALL_GICP and SMALL_VGICP backends): on Jazzy, sudo apt install ros-jazzy-small-gicp-vendor before building is enough. For Humble, a manual or no-sudo build, see local build.

No ROS install? Build the Docker image and check it in one command:

docker build -f docker/Dockerfile -t lidar_localization_ros2 .
docker run --rm lidar_localization_ros2 /ws/src/lidar_localization_ros2/docker/smoke_status.sh

Quick start

  1. Start the LiDAR driver, and odometry if you have it.
  2. Run quickstart with your map:
   ros2 run lidar_localization_ros2 quickstart.py --map /absolute/path/to/map.pcd
  1. Check that it is tracking:
   ros2 run lidar_localization_ros2 check_lidar_localization_bringup.py --profile standalone

Quickstart finds the cloud and IMU topics, /clock, an odom -> base TF and the LiDAR frame, and prints what it picked on its Discovery: line. Then it starts the localizer and RViz. On the first run it searches the whole map for the robot; next time it restores the pose saved for the same map. If the search finds no safe match, it asks you for 2D Pose Estimate in RViz (press P, click the robot, drag along its heading) instead of guessing.

CHANGELOG

Changelog

Unreleased

1.11.0 - 2026-11-18

Upgrading: no configuration needs changing on Humble or Jazzy, and every new setting defaults to the old behaviour: cloud_reliable_qos (false; Foxy only, ignored with a warning elsewhere), enable_stale_reset_replay (false) and imu_smoother_window_size (50). param/mid360_legged_low_resource.yaml is a new preset and needs odometry. ROS 2 Foxy is now a best-effort target that builds from main (ndt_omp_ros2 needs its humble branch at rsasaki0109/ndt_omp_ros2#18 or later for PCL 1.10). The fitness score’s compact kd-tree gives the same scores with less memory. One behaviour differs: a scan seeded from the odometry TF is no longer aligned again from the IMU prediction after a rejection; scans without an odometry seed keep that retry. The foxy, humble and jazzy branches are gone: build every distribution from main, or check out the tags archive/foxy, archive/humble and archive/jazzy for their last commits.

Added

  • Cross-session results on the Go2 (JEPLO): the map from one recording, the scans from another, no initial pose (benchmark.md, tools/benchmark/suites/go2_jeplo_cross_session.yaml). Long_Stairs and Outdoor2 (same route, 1.5 h apart) localized each other in all 4 runs, 0.02 m off. In the capture room the EIL_Mix map localized four other runs in all 8 tries; the EIL_Box map started 4 of 6 runs 1-5.5 m off, and the Long_Stairs map let tracking slide up to 2.5 m where the props had moved. The README GIF now uses the Long_Stairs map with the Outdoor2 scans instead of a map from the same recording. jeplo_to_pc2_bag.py --duration keeps the first seconds of a bag.
  • param/mid360_legged_low_resource.yaml, for a Jetson Orin Nano/NX on a Unitree Go2 or G1-class robot with a MID-360: mid360_legged.yaml with a 0.5 m scan voxel, two NDT threads, 15 iterations, odometry TF seeds, no pose timer and the MID-360’s acceleration in g. It needs odometry. With the localizer pinned to two x86 cores and RKO-LIO beside it, on JEPLO EIL_Stairs (Go2, motion capture) it took about 0.2 cores instead of 0.27 at the same error (0.067 m against 0.077 m), and on Koide outdoor_hard_02b 0.45-0.50 cores instead of 0.70 (0.23 m against 0.25 m). Without odometry the coarse scan locked onto the wrong stair level, so keep mid360_legged.yaml there (mid360_legged_jetson.md, benchmark.md).
  • imu_smoother_window_size (default 50, as before): the scans the IMU smoother re-optimizes on every update, a quarter of the node’s CPU with a 0.5 m scan. 20 saved 18% of the CPU on the Go2 bag, but 20 and 30 lost the pose for 40 s or more on the Koide outdoor bag, so no preset lowers it.

  • The replay harnesses report CPU and memory: boreas_replay.py, soak_replay.py and run_koide_public_bag.py sample the localizer’s CPU time from /proc next to its memory, and summary.json gives the cores in use (mean and p95), CPU per second of data and per scan, peak and steady resident and anonymous memory, pose latency, and the scans processed and accepted. boreas_replay.py replays any fixture of the same layout (--points-topic, --imu-topic, --base-frame), runs the localizer under --wrap COMMAND (e.g. taskset or a cgroup) and starts --companion nodes such as an odometry, whose resources it samples too; run_koide_public_bag.py takes --preset, --set and --wrap.

  • ROS 2 Foxy builds, passes its tests and runs, as a best-effort target (Foxy is end-of-life); CI builds and tests it. Humble and Jazzy build and behave as before. On Foxy:
    • ndt_omp_ros2 builds with Foxy’s PCL 1.10 from its humble branch since rsasaki0109/ndt_omp_ros2#18.
    • The cloud subscription keeps the best-effort sensor QoS by default: Foxy has no qos_overrides.<topic>.subscription.reliability parameter. The ~1 MB clouds of the Boreas replay then lose fragments in transport, and only about 970 of 1158 scans reach the node. Set the new cloud_reliable_qos: true to subscribe reliably there (all 1158 scans arrive, same RMSE). Humble and Jazzy ignore the parameter, with a warning, and keep using qos_overrides.
    • The node uses a small TF listener of its own in place of Foxy’s, which can crash or hang when the node is destroyed.
    • run_koide_public_bag.py and the other helpers that read bags need rosbag2_py, which Foxy does not have. The tools/benchmark replays use ros2 bag play --clock, which Foxy’s rosbag2 lacks, and Foxy cannot read the metadata of bags written by newer rosbag2 releases.
  • A reset older than the scan it is applied to is tracked up to that scan, opt-in with the localizer parameter enable_stale_reset_replay (default false; also stale_reset_replay_min_age_sec, 0.5, and stale_reset_replay_max_age_sec, 20.0). A global localization answer reaches the localizer seconds after its scan, metres behind a moving vehicle, which restarted there with no velocity and rejected every later scan. The localizer now keeps its recent scans, tracks from the reset through them as in normal tracking, and moves the reset to the newest scan with the velocity tracked on the way; a replay that loses track leaves the reset as it was. On the Boreas closed loop with the fast settings, 5 of 10 stops of 10 s recovered, against none before, with no wrong pose accepted (global_localization.md).

Changed

  • The fitness score’s search tree no longer copies the map. The fitness and the inlier ratio were scored on PCL’s FLANN kd-tree over the registration target, which holds two copies of its coordinates and an index mapping: about 100 MB for the 2.0M-point Koide outdoor map. CompactKdTree indexes the target in place (13 MB there) and returns the same squared distances, so the scores, the gate and the trajectories do not change. Map loading also frees the file as read before the target is built and no longer copies it for /initial_map or converts an xyz map through a temporary cloud. With the localizer pinned to two cores (benchmark): on Koide outdoor_hard_02b the node holds 218 instead of 300 MB anonymous (272 instead of 356 MB resident) and runs in a 224 MB memory cgroup, where it was killed at 256 MB before; on JEPLO EIL_Stairs (a 580k-point map) 44 instead of 77 MB; on the Boreas fixture (local map crops) 272

  • The replay harnesses report CPU and memory: boreas_replay.py, soak_replay.py and run_koide_public_bag.py sample the localizer’s CPU time from /proc next to its memory, and summary.json gives the cores in use (mean and p95), CPU per second of data and per scan, peak and steady resident and anonymous memory, pose latency, and the scans processed and accepted. boreas_replay.py replays any fixture of the same layout (--points-topic, --imu-topic, --base-frame), runs the localizer under --wrap COMMAND (e.g. taskset or a cgroup) and starts --companion nodes such as an odometry, whose resources it samples too; run_koide_public_bag.py takes --preset, --set and --wrap.

    • ndt_omp_ros2 builds with Foxy’s PCL 1.10 from its humble branch since rsasaki0109/ndt_omp_ros2#18.
    • The cloud subscription keeps the best-effort sensor QoS by default: Foxy has no qos_overrides.<topic>.subscription.reliability parameter. The ~1 MB clouds of the Boreas replay then lose fragments in transport, and only about 970 of 1158 scans reach the node. Set the new cloud_reliable_qos: true to subscribe reliably there (all 1158 scans arrive, same RMSE). Humble and Jazzy ignore the parameter, with a warning, and keep using qos_overrides.
    • The node uses a small TF listener of its own in place of Foxy’s, which can crash or hang when the node is destroyed.
    • run_koide_public_bag.py and the other helpers that read bags need rosbag2_py, which Foxy does not have. The tools/benchmark replays use ros2 bag play --clock, which Foxy’s rosbag2 lacks, and Foxy cannot read the metadata of bags written by newer rosbag2 releases.

A global localization answer reaches the localizer seconds after its scan, metres behind a moving vehicle, which restarted there with no velocity and rejected every later scan. The localizer now keeps its recent scans, tracks from the reset through them as in normal tracking, and moves the reset to the newest scan with the velocity tracked on the way; a replay that loses track leaves the reset as it was. On the Boreas closed loop with the fast settings, 5 of 10 stops of 10 s recovered, against none before, with no wrong pose accepted (global_localization.md).

README.md

lidar_localization_ros2

Map-based 3D LiDAR localization for ROS 2 and Nav2.

Handheld Livox MID-360, ~390 m outdoors on a prior map, including stretches where the scans do not match the map and a section outside it. Each scan is matched to the map with NDT; RKO-LIO odometry predicts the motion between scans and carries the pose where matching fails. The error is 0.26 m RMSE for the whole run, in an offline replay started from the ground-truth pose (Koide Hard Point Cloud Localization Dataset outdoor_hard_02b, CC BY 4.0). How this was made · more runs

Global localization on a Unitree Go2 (upside-down Livox MID-360), started with no initial pose, on a map from a different recording: the map is built from the run Long_Stairs, the scans come from the run Outdoor2, recorded 1.5 h later along the same route (the room was not rearranged in between). The quickstart searches the whole map: each query returns 32 ranked places (circles sized by score) in 2.6 s, and the answer is accepted when two queries agree after the odometry motion. The first pose came 13.3 s into the run, 6.4 s after the first search, 0.01 m from the motion-capture ground truth. Tracking then follows the robot out of the capture room and down the long staircase, within 0.02 m (median) of the ground truth where it exists (the room). Offline replay at 1× (JEPLO dataset, GPL-3.0; this GIF is derived from it and shared under the same licence). How this was made · pairs with moved props, including failures

Give it a point cloud map (.pcd or .ply) and a LiDAR stream; it publishes the robot pose in the map. It finds the starting pose by itself, uses odometry and IMU when you have them, and works standalone or as the localization source for Nav2.

Install

ROS 2 Jazzy is the main target; Humble is supported. Foxy is end-of-life and supported on a best-effort basis: CI builds and tests it, and its differences are listed in the changelog under Unreleased.

All of them build from main. The old foxy, humble and jazzy branches are no longer kept; their last commits are the tags archive/foxy, archive/humble and archive/jazzy. ROS 2 Dashing, which main does not support, has the frozen dashing branch.

mkdir -p ~/lidarloc_ws/src
cd ~/lidarloc_ws/src
git clone https://github.com/rsasaki0109/lidar_localization_ros2.git
cd lidar_localization_ros2
scripts/bootstrap_colcon_workspace.sh --build
source ~/lidarloc_ws/install/setup.bash

This builds ndt_omp_ros2 and this package, about 30 minutes on an 8-core machine. small_gicp is optional (SMALL_GICP and SMALL_VGICP backends): on Jazzy, sudo apt install ros-jazzy-small-gicp-vendor before building is enough. For Humble, a manual or no-sudo build, see local build.

No ROS install? Build the Docker image and check it in one command:

docker build -f docker/Dockerfile -t lidar_localization_ros2 .
docker run --rm lidar_localization_ros2 /ws/src/lidar_localization_ros2/docker/smoke_status.sh

Quick start

  1. Start the LiDAR driver, and odometry if you have it.
  2. Run quickstart with your map:
   ros2 run lidar_localization_ros2 quickstart.py --map /absolute/path/to/map.pcd
  1. Check that it is tracking:
   ros2 run lidar_localization_ros2 check_lidar_localization_bringup.py --profile standalone

Quickstart finds the cloud and IMU topics, /clock, an odom -> base TF and the LiDAR frame, and prints what it picked on its Discovery: line. Then it starts the localizer and RViz. On the first run it searches the whole map for the robot; next time it restores the pose saved for the same map. If the search finds no safe match, it asks you for 2D Pose Estimate in RViz (press P, click the robot, drag along its heading) instead of guessing.

The quickstart searches the whole map: each query returns 32 ranked places (circles sized by score) in 2.6 s, and the answer is accepted when two queries agree after the odometry motion. The first pose came 13.3 s into the run, 6.4 s after the first search, 0.01 m from the motion-capture ground truth. All of them build from main. The old foxy, humble and jazzy branches are no longer kept; their last commits are the tags archive/foxy, archive/humble and archive/jazzy. ROS 2 Dashing, which main does not support, has the frozen dashing branch.

README.md

lidar_localization_ros2

Map-based 3D LiDAR localization for ROS 2 and Nav2.

Handheld Livox MID-360, ~390 m outdoors on a prior map, including stretches where the scans do not match the map and a section outside it. Each scan is matched to the map with NDT; RKO-LIO odometry predicts the motion between scans and carries the pose where matching fails. The error is 0.26 m RMSE for the whole run, in an offline replay started from the ground-truth pose (Koide Hard Point Cloud Localization Dataset outdoor_hard_02b, CC BY 4.0). How this was made · more runs

Global localization on a Unitree Go2 (upside-down Livox MID-360), started with no initial pose, on a map from a different recording: the map is built from the run Long_Stairs, the scans come from the run Outdoor2, recorded 1.5 h later along the same route (the room was not rearranged in between). The quickstart searches the whole map: each query returns 32 ranked places (circles sized by score) in 2.6 s, and the answer is accepted when two queries agree after the odometry motion. The first pose came 13.3 s into the run, 6.4 s after the first search, 0.01 m from the motion-capture ground truth. Tracking then follows the robot out of the capture room and down the long staircase, within 0.02 m (median) of the ground truth where it exists (the room). Offline replay at 1× (JEPLO dataset, GPL-3.0; this GIF is derived from it and shared under the same licence). How this was made · pairs with moved props, including failures

Give it a point cloud map (.pcd or .ply) and a LiDAR stream; it publishes the robot pose in the map. It finds the starting pose by itself, uses odometry and IMU when you have them, and works standalone or as the localization source for Nav2.

Install

ROS 2 Jazzy is the main target; Humble is supported. Foxy is end-of-life and supported on a best-effort basis: CI builds and tests it, and its differences are listed in the changelog under Unreleased.

All of them build from main. The old foxy, humble and jazzy branches are no longer kept; their last commits are the tags archive/foxy, archive/humble and archive/jazzy. ROS 2 Dashing, which main does not support, has the frozen dashing branch.

mkdir -p ~/lidarloc_ws/src
cd ~/lidarloc_ws/src
git clone https://github.com/rsasaki0109/lidar_localization_ros2.git
cd lidar_localization_ros2
scripts/bootstrap_colcon_workspace.sh --build
source ~/lidarloc_ws/install/setup.bash

This builds ndt_omp_ros2 and this package, about 30 minutes on an 8-core machine. small_gicp is optional (SMALL_GICP and SMALL_VGICP backends): on Jazzy, sudo apt install ros-jazzy-small-gicp-vendor before building is enough. For Humble, a manual or no-sudo build, see local build.

No ROS install? Build the Docker image and check it in one command:

docker build -f docker/Dockerfile -t lidar_localization_ros2 .
docker run --rm lidar_localization_ros2 /ws/src/lidar_localization_ros2/docker/smoke_status.sh

Quick start

  1. Start the LiDAR driver, and odometry if you have it.
  2. Run quickstart with your map:
   ros2 run lidar_localization_ros2 quickstart.py --map /absolute/path/to/map.pcd
  1. Check that it is tracking:
   ros2 run lidar_localization_ros2 check_lidar_localization_bringup.py --profile standalone

Quickstart finds the cloud and IMU topics, /clock, an odom -> base TF and the LiDAR frame, and prints what it picked on its Discovery: line. Then it starts the localizer and RViz. On the first run it searches the whole map for the robot; next time it restores the pose saved for the same map. If the search finds no safe match, it asks you for 2D Pose Estimate in RViz (press P, click the robot, drag along its heading) instead of guessing.

1.11.0 - 2026-11-18

Upgrading: no configuration needs changing on Humble or Jazzy, and every new setting defaults to the old behaviour: cloud_reliable_qos (false; Foxy only, ignored with a warning elsewhere), enable_stale_reset_replay (false) and imu_smoother_window_size (50). param/mid360_legged_low_resource.yaml is a new preset and needs odometry. ROS 2 Foxy is now a best-effort target that builds from main (ndt_omp_ros2 needs its humble branch at rsasaki0109/ndt_omp_ros2#18 or later for PCL 1.10). The fitness score’s compact kd-tree gives the same scores with less memory. One behaviour differs: a scan seeded from the odometry TF is no longer aligned again from the IMU prediction after a rejection; scans without an odometry seed keep that retry. The foxy, humble and jazzy branches are gone: build every distribution from main, or check out the tags archive/foxy, archive/humble and archive/jazzy for their last commits.

Added

  • Cross-session results on the Go2 (JEPLO): the map from one recording, the scans from another, no initial pose (benchmark.md, tools/benchmark/suites/go2_jeplo_cross_session.yaml). Long_Stairs and Outdoor2 (same route, 1.5 h apart) localized each other in all 4 runs, 0.02 m off. In the capture room the EIL_Mix map localized four other runs in all 8 tries; the EIL_Box map started 4 of 6 runs 1-5.5 m off, and the Long_Stairs map let tracking slide up to 2.5 m where the props had moved. The README GIF now uses the Long_Stairs map with the Outdoor2 scans instead of a map from the same recording. jeplo_to_pc2_bag.py --duration keeps the first seconds of a bag.
  • param/mid360_legged_low_resource.yaml, for a Jetson Orin Nano/NX on a Unitree Go2 or G1-class robot with a MID-360: mid360_legged.yaml with a 0.5 m scan voxel, two NDT threads, 15 iterations, odometry TF seeds, no pose timer and the MID-360’s acceleration in g. It needs odometry. With the localizer pinned to two x86 cores and RKO-LIO beside it, on JEPLO EIL_Stairs (Go2, motion capture) it took about 0.2 cores instead of 0.27 at the same error (0.067 m against 0.077 m), and on Koide outdoor_hard_02b 0.45-0.50 cores instead of 0.70 (0.23 m against 0.25 m). Without odometry the coarse scan locked onto the wrong stair level, so keep mid360_legged.yaml there (mid360_legged_jetson.md, benchmark.md).
  • imu_smoother_window_size (default 50, as before): the scans the IMU smoother re-optimizes on every update, a quarter of the node’s CPU with a 0.5 m scan. 20 saved 18% of the CPU on the Go2 bag, but 20 and 30 lost the pose for 40 s or more on the Koide outdoor bag, so no preset lowers it.

  • The replay harnesses report CPU and memory: boreas_replay.py, soak_replay.py and run_koide_public_bag.py sample the localizer’s CPU time from /proc next to its memory, and summary.json gives the cores in use (mean and p95), CPU per second of data and per scan, peak and steady resident and anonymous memory, pose latency, and the scans processed and accepted. boreas_replay.py replays any fixture of the same layout (--points-topic, --imu-topic, --base-frame), runs the localizer under --wrap COMMAND (e.g. taskset or a cgroup) and starts --companion nodes such as an odometry, whose resources it samples too; run_koide_public_bag.py takes --preset, --set and --wrap.

  • ROS 2 Foxy builds, passes its tests and runs, as a best-effort target (Foxy is end-of-life); CI builds and tests it. Humble and Jazzy build and behave as before. On Foxy:
    • ndt_omp_ros2 builds with Foxy’s PCL 1.10 from its humble branch since rsasaki0109/ndt_omp_ros2#18.
    • The cloud subscription keeps the best-effort sensor QoS by default: Foxy has no qos_overrides.<topic>.subscription.reliability parameter. The ~1 MB clouds of the Boreas replay then lose fragments in transport, and only about 970 of 1158 scans reach the node. Set the new cloud_reliable_qos: true to subscribe reliably there (all 1158 scans arrive, same RMSE). Humble and Jazzy ignore the parameter, with a warning, and keep using qos_overrides.
    • The node uses a small TF listener of its own in place of Foxy’s, which can crash or hang when the node is destroyed.
    • run_koide_public_bag.py and the other helpers that read bags need rosbag2_py, which Foxy does not have. The tools/benchmark replays use ros2 bag play --clock, which Foxy’s rosbag2 lacks, and Foxy cannot read the metadata of bags written by newer rosbag2 releases.
  • A reset older than the scan it is applied to is tracked up to that scan, opt-in with the localizer parameter enable_stale_reset_replay (default false; also stale_reset_replay_min_age_sec, 0.5, and stale_reset_replay_max_age_sec, 20.0). A global localization answer reaches the localizer seconds after its scan, metres behind a moving vehicle, which restarted there with no velocity and rejected every later scan. The localizer now keeps its recent scans, tracks from the reset through them as in normal tracking, and moves the reset to the newest scan with the velocity tracked on the way; a replay that loses track leaves the reset as it was. On the Boreas closed loop with the fast settings, 5 of 10 stops of 10 s recovered, against none before, with no wrong pose accepted (global_localization.md).
